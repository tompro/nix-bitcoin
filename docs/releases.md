# Automatic releases for this fork

After a push or PR merge to `master`, the complete **nix-bitcoin tests** workflow
must succeed, including configuration/lint checks and the VM test matrix. Only
then does [the release workflow](../.github/workflows/release.yml) publish a
GitHub Release. Failed, cancelled, PR, and other-branch runs cannot publish.

No manual tag, draft approval, or repository changelog is required. The release
notes are generated by GitHub from Git history and merged PRs. Put useful change
summaries and migration warnings in PR descriptions and linked documentation.

## Tags and commit selection

Tags use the UTC release date and a daily counter, for example:

- `v2026.11.04.1`
- `v2026.11.04.2` for another release that day
- `v2026.11.05.1` on the following day

The tag always points to the **exact commit whose master CI passed**, not the
possibly newer master tip. The release is published immediately and marked as
latest. If an older CI run finishes after a newer commit has already been
released, it is skipped rather than moving latest backwards.

Publishing is serialized. Rerunning a successful release does not create another
release or overwrite an existing one. If tag creation succeeded but publishing
failed, rerun the failed release job: it reuses the existing tag after checking
its remote target. Tag collisions fail safely; tags are never moved. Existing
manual releases, including drafts, are left unchanged.

The workflow must be merged into the default branch before GitHub can trigger
it. After merging this change, a completed successful master CI run can publish
without further approval. The publishing API is not called during PR tests;
the offline policy tests mock all GitHub writes.

## Permissions and consumers

The job executes trusted publisher code from `master`, accepts only same-repo
master push CI events, rechecks the live CI result, and checks commit ancestry.
It never downloads or executes PR artifacts. It uses `GITHUB_TOKEN` with release
write permission; no PAT or private signing key is stored in Actions.

The automatically created tags are **unsigned lightweight tags**. Flake
consumers can select one explicitly:

```nix
inputs.nix-bitcoin.url = "github:tompro/nix-bitcoin/v2026.11.04.1"; # example
```

The legacy `helper/push-release.sh`, `helper/fetch-release`, and deployment-shell
updater still target **fort-nix/nix-bitcoin** and trust its specific maintainer
key. These releases do not create signed `nar-hash.txt` assets or change that
trust path. Use an explicit fork flake input; independently verified fork
signatures and migration of the legacy updater would be a separate security
change. GitHub publication and Nix content hashes do not replace independent
maintainer-signature verification.

## LND 0.21.8 tag update

LND is pinned to the signed `v0.21.8-beta` tag, ahead of a published GitHub
release. Back up wallet/channel state before deploying and review the
[upstream notes](https://github.com/lightningnetwork/lnd/blob/v0.21.8-beta/docs/release-notes/release-notes-0.21.8.md).
In particular, funding publication errors now retain pending channels for
recovery; permanently unpublishable transactions may require manual cleanup.

With LND enabled, the module also defaults to disabling host MPTCP and sets
`GODEBUG=multipathtcp=0` for LND, including in isolated network namespaces.
These mitigate the demonstrated CVE-2026-98432 exploit path but do not fix
the kernel: update the host kernel and reboot. See
[deployment and verification instructions](services.md#lnd-linux-kernel-mptcp-mitigation).

## Upgrade reminders for the initial maintained-fork update

The dependency/configuration changes in PR #20 require operator review even
though releases are automatic:

- Back up databases and wallet/channel state before deployment. Bitcoin Core
  moves from 31.1 to 32.1; review RPC/PSBT changes and txindex downgrade limits.
- LND 0.21.6 mitigates the demonstrated MPTCP exploit path for CVE-2026-98432,
  but the underlying vulnerability still requires a patched host kernel and
  reboot. Updating this flake alone does not update a consumer's kernel.
- lnurl-mint 0.13 changes LUD-26 wallet registration and derivation formats.
  Wallet clients must support it; legacy registrations retain their old
  derivation until explicitly migrated. Consult the pinned upstream README.
- CDK's older 0.17-to-0.18 database migration requirements still apply.
- Bitcoin Core 29.x is EOL; the named `bitcoind_29` compatibility package remains.
- electrs stays at the compatible 0.11 package. Moving to 0.12 needs REST
  integration and an index rebuild, not an automatic package bump.
